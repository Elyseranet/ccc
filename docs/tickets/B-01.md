## Pourquoi

Aujourd'hui, `server/database/data-source.ts` ne sert que la CLI TypeORM : il lit `process.env` via `dotenv` et charge les entités par glob. Nitro ne peut pas l'utiliser tel quel, parce que le bundle ne résout pas les globs. Le projet n'a pas non plus de lanceur de tests (aucun script `test` dans `package.json`).

## Périmètre

1. **DataSource runtime**
   - `server/utils/database.util.ts` : `useDataSource()` initialise une seule fois, de façon paresseuse, une `DataSource` construite depuis `useRuntimeConfig().database`.
   - Elle reprend `SnakeNamingStrategy` et pose `synchronize: false`.
   - Les entités sont listées **explicitement** dans `server/database/entities/index.ts`, un registre partagé par la CLI et le runtime.
   - Un plugin Nitro journalise l'échec d'initialisation, sans exposer la chaîne de connexion.
2. **tsconfig CLI** : `tsconfig.typeorm.json` doit pouvoir compiler `shared/enums/**`, parce que les entités importent ces enums. On élargit `rootDir` et `include`, puis on vérifie que `db:migration:run` tourne toujours.
3. **Erreurs**
   - `shared/enums/api-error-code.enum.ts` (`API_ERROR_CODE`) et `shared/interfaces/api/error.interface.ts` (`IApiError { statusCode, code, message, details? }`).
   - `server/utils/http/api-error.util.ts` : des fabriques `badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`, `unprocessable` et `gone`, construites sur `createError`.
   - Le message d'une erreur 5xx est générique ; le détail ne part que dans les logs.
4. **Validation d'input**
   - `server/utils/http/validation.util.ts` enveloppe `readValidatedBody`, `getValidatedQuery` et `getValidatedRouterParams` de h3, avec des schémas `zod`.
   - Avant d'ajouter la dépendance, vérifier `npm ls axios` : aucune entrée ne doit apparaître.
   - Un identifiant invalide renvoie 400, pas 404 ni 500.
5. **Pagination** : `shared/interfaces/api/pagination.interface.ts` (`IPaginated<T> { items, total, page, pageSize }`) et `server/utils/http/pagination.util.ts`. Les bornes vivent dans `server/consts/pagination.const.ts`.
6. **Limiteur de débit**
   - `server/utils/http/rate-limit.util.ts` : une fenêtre glissante en mémoire, par IP et par clé de route.
   - Les valeurs viennent de `runtimeConfig.rateLimit.*` ; aucune valeur en dur.
   - Il suffit pour une instance unique. Le mode de déploiement n'étant pas spécifié, cette limite est documentée.
7. **Logs structurés**
   - `server/utils/logger.util.ts` écrit du JSON en ligne : `event`, `level`, `requestId`, `route`, `durationMs`.
   - Les noms d'événements vivent dans `server/consts/log-event.const.ts`.
   - Un middleware `server/middleware/request-id.ts` pose l'en-tête `X-Request-Id`.
   - Aucun `console.log` sauvage. Le seed legacy existant passe sur ce logger.
8. **Santé** : `GET /api/v1/health`, qui fait un `SELECT 1` et renvoie `{ status }` sans aucun détail d'infrastructure.
9. **Tests** : Vitest, avec les scripts `test:run` (unitaires) et `test:api` (intégration).
   - Les tests d'API utilisent `@nuxt/test-utils/e2e` sur une base dédiée, dont le nom est fourni par l'environnement (`NUXT_DATABASE_DATABASE` de test).
   - Vérifier `npm ls axios` après installation.
   - La stratégie est coordonnée avec `qa-tester`, propriétaire des suites.
10. **Préfixe** : toutes les routes vivent sous `server/api/v1/…`, au format `resource.method.ts`.

## Critères d'acceptation

- [ ] `npm run test:run` est vert, et couvre au moins les fabriques d'erreur, la pagination (bornes, valeurs non numériques) et le limiteur (dépassement, fenêtre).
- [ ] `GET /api/v1/health` répond 200 base joignable, 503 base coupée, sans fuite du message pg.
- [ ] `npm run db:migration:run` et `db:migration:revert` fonctionnent après l'élargissement du tsconfig.
- [ ] `grep -rn "console\.\(log\|info\|error\)" server/` ne trouve rien, en dehors du logger.
- [ ] Aucun secret dans le diff (gitleaks) ; `npm audit` sans `high` ni `critical`.
- [ ] Le README documente les nouvelles variables d'environnement (rate limit, base de test).

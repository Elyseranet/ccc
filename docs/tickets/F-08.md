## Endpoints

- `GET /api/v1/admin/editions/{id}/matchs?statut=&tour=&poule=` → `IAdminMatch` (C6, B-12). L'interface étend `IMatch` (`../../src/interfaces/admin-match.interface.ts`) avec `sides[].recordedScore`, `recordedAt`, `validatedAt` et `validatedBy`. Le paramètre `poule=` sert le sélecteur « Toutes les poules / Poule n » de la maquette. Le front n'utilise `recordedScore` que dans l'admin : aucune route publique ne le renvoie (test de B-12). `GET /editions/{id}/poules`.
- **Correspondance filtres → statuts**, définie par le front. Elle se déduit des compteurs de la maquette : À traiter 37 = Saisis 7 + Sans score 30, et 37 + Validés 68 = 105 matchs de poule, soit le « 68 / 105 » de l'accueil.

  | Filtre | `MATCH_STATUS` |
  |---|---|
  | À traiter | `RECORDED`, `SCHEDULED` |
  | Saisis | `RECORDED` |
  | Sans score | `SCHEDULED` |
  | Validés | `VALIDATED` |

  `RESULT_UNKNOWN` n'apparaît que dans les éditions d'archive, en lecture seule ; ce statut n'est dans aucun filtre. La table vit dans `src/consts/admin-match-filters.const.ts`, et l'enum des filtres dans `src/enums/`.
- `PUT /matchs/{id}/score` : « Enregistrer », sans rendre le score opposable.
- `POST /matchs/{id}/validation` : « Valider ». Idempotent ; **la réponse contient l'état recalculé** (Spec API), donc on ne refait pas de GET.
- Erreurs à traduire en messages : 409 (match déjà validé, conflit avec une autre session), 422 (RG22), 403, 401, et réseau. `POST /matchs/{id}/correction` n'est ni consommé ni déclaré dans `API_ROUTES` (F-18).

## Contrôle de version obligatoire (SEC-Q, T-SEC-08, contrat figé fd49496)

- Saisie (`PUT /matchs/{id}/score`) et validation (`POST /matchs/{id}/validation`) envoient (la correction, alignée sur 428/412 par la décision f924eda, relève de F-18) `If-Match: "<version>"`, avec la `version` lue dans `IAdminMatch` (liste `GET /admin/editions/{id}/matchs`).
- La réponse d'une écriture réussie porte la nouvelle version (`IAdminMatch.version`, `IMatchValidationResult.match.version`) : on enchaîne saisie puis validation sans relire.
- **412 `VERSION_CONFLICT`** (`details.currentVersion`) : message traduit « Ce match a été modifié, rechargez », la ligne est rechargée. **428 `PRECONDITION_REQUIRED`** : bug front, jamais un cas utilisateur (test unitaire qui garantit l'en-tête sur chaque écriture).
- Précisions d'implémentation (back-lead, 2026-11-01) : un **rejeu à l'identique** (même PUT de scores, ou validation d'un match déjà validé aux mêmes scores) répond **200 sans effet**, même avec une version périmée (idempotence B-12, utile pour un nouvel essai réseau) ; une version périmée avec des scores différents répond 412. Une **validation à version à jour mais dont les scores du corps diffèrent du score saisi** répond **409 `SCORE_MISMATCH`** (correction du back-lead après revue avec le chef de projet, 2026-11-01) : comme 428, c'est un **défaut du front** (il n'a pas renvoyé les scores lus), traité par un message générique, jamais comme un cas utilisateur. La version périmée reste **412 `VERSION_CONFLICT`**. `MATCH_VERSION_CONFLICT` n'existe plus.
- Référence : `docs/tickets/T-SEC-08.md`, section « Contrat figé avec le frontend-lead (2026-11-01) ».

## Périmètre : tous les tours, avec un filtre par tour

Décision utilisateur 1b7483d5 (`docs/design/ux/decisions.md`) : la file couvre les poules **et** la phase finale, car aucun écran admin ne saisit les scores du bracket (F-03-BRK ne couvre que la page publique). Elle charge tous les matchs de l'édition et les filtre dans le navigateur :
- `origam-select` « Tour » : « Tous les tours », puis les seuls tours présents dans l'édition, dans l'ordre de `ROUND_KIND`, libellés `ROUND_LABELS`. Valeur par défaut : le tour en cours, soit le premier tour qui a encore un match saisi ou à jouer (le dernier tour si tout est validé). Il est calculé au chargement de la liste, pas après chaque écriture. `?tour=` porte le choix (`ROUND_KIND` ou `all`).
- `origam-select` « Poule » : affiché seulement pour le tour « Poules » (`?poule=`), à droite du sélecteur de tour.
- Les compteurs des quatre puces suivent le tour et la poule actifs ; le `aria-label` du groupe le dit.
- Le contrôle RG22 en phase finale (cible 10) vient de `score-rules.util`.

Maquette : `admin-matchs.html` (ui, 7c076c66 et b795a501). L'état « phase finale, cible 10 » du formulaire n'est pas dessiné.

## Endpoints

| Méthode et chemin | Accès | Règles |
|---|---|---|
| `POST /api/v1/competiteurs` | administrateur | P1, cas 2 : crée le compétiteur, le compte `INVITED`, l'invitation, puis envoie l'email |
| `GET /api/v1/auth/invitation/{jeton}` | public | 200 avec un prénom et un pseudo à pré-remplir ; **410** si le lien est expiré ou consommé ; 404 si le jeton est inconnu |
| `POST /api/v1/auth/invitation/{jeton}` | public, jeton valide | définit le mot de passe, complète le profil (nom, prénom, pseudo, téléphone, selon `parcours.md` ; l'avatar se téléverse ensuite par `PUT /moi/avatar`, B-16), consomme le jeton, ouvre une session ; 410 si le jeton est consommé ou expiré |
| `POST /api/v1/competiteurs/{id}/invitation` | administrateur | renvoi de l'invitation, qui **invalide l'ancien lien** (A14). Ajout à la Spec API |

## Périmètre

1. **Table `invitations`** (migration M2 de B-08, ou M2 bis) : `id`, `user_id`, `token_hash` (SHA-256), `expires_at`, `consumed_at?`, `created_at`.
   - Le jeton en clair (32 octets aléatoires, encodés en base64url) n'existe que dans l'email.
   - Un renvoi invalide les invitations précédentes.
2. **Port d'envoi**
   - `../../src/server/services/mail/mail.port.ts`, avec ses adaptateurs dans `../../src/server/services/mail/adapters/`.
   - Adaptateur unique **SMTP via nodemailer** (A3) : Mailpit en développement, fournisseur SMTP de production via `runtimeConfig.mail.*` (hôte, port, utilisateur, mot de passe, expéditeur), aucun secret en dur. Un adaptateur de test qui capture les envois.
   - Avant l'ajout : `npm ls axios` vide après installation de nodemailer.
   - Durée de validité : `INVITATION_TTL_DAYS = 7` dans `../../src/server/consts/invitation.const.ts` (A14).
   - Un appel HTTP au fournisseur passe par `fetch` natif, avec `AbortSignal.timeout`. Si l'adaptateur est SMTP, vérifier `npm ls axios` avant d'ajouter la dépendance.
3. **Fiabilité de l'envoi**
   - La transaction crée le compétiteur, l'utilisateur et l'invitation, et l'envoi part **après commit**.
   - En cas d'échec : la réponse de la route le dit (`invitationSent: false`), un événement est journalisé, et le renvoi reste possible.
   - La table outbox citée par ARCHITECTURE n'est **pas** retenue à ce volume, sauf avis contraire en revue.
4. **Unicité de l'email** : un email déjà rattaché à un compte renvoie 409 `EMAIL_ALREADY_USED`, comme le prévoit la SF (« Ce que voit l'utilisateur quand ça échoue »).
5. **Premier administrateur** : la commande `npm run user:create-admin` livrée par B-08 crée le compte `ADMIN` sans mot de passe. B-09 lui fait **générer et afficher le lien d'invitation** (même jeton, même durée de 7 jours, A14), en le construisant depuis `runtimeConfig.public.siteUrl`. Le jeton en clair n'est affiché qu'une fois sur la sortie standard et n'est jamais journalisé. Test : la commande produit un lien valide, consommable une seule fois.
6. **Homonymes** : la SF ne dit pas quoi faire (P1, Échecs). Ce ticket ne bloque pas sur un homonyme ; la recherche à autocomplétion de B-05 sert à l'éviter côté UI.

## Garde-fous de configuration en production (décision back-lead du 2026-10-21, revue de 6c2d36f)

Avec les valeurs par défaut de nuxt.config, `public.siteUrl` vaut `http://localhost:3000`, `mail.host` vaut `localhost` (Mailpit), et rien n'empêche `NUXT_MAIL_TRANSPORT=capture`. Une image déployée avec une configuration oubliée enverrait des liens d'invitation vers localhost, ou avalerait les emails en silence.
- Un indicateur **explicite** `runtimeConfig.strictRuntimeConfig` (`NUXT_STRICT_RUNTIME_CONFIG`), **faux par défaut**, vrai dans l'image de production (`ENV NUXT_STRICT_RUNTIME_CONFIG=true` dans l'étage runner du Dockerfile). Il ne repose pas sur `NODE_ENV`, puisque le build de test des API est lui aussi un build de production (même logique que L3, `secureCookie`).
- Quand l'indicateur est vrai, le démarrage échoue, avec un message qui nomme la variable, jamais sa valeur, si :
  - `public.siteUrl` n'est pas en `https:` ou désigne `localhost` ou `127.0.0.1` ;
  - `mail.transport` n'est pas `smtp` ;
  - `mail.host` vaut `localhost` ou `127.0.0.1` ;
  - `mail.from` est vide.
- Tests unitaires : chaque cas refusé avec l'indicateur, et tout accepté sans l'indicateur. Les tests d'API ne posent pas l'indicateur et restent inchangés.
- README, section déploiement Coolify : les variables obligatoires en production (`NUXT_PUBLIC_SITE_URL`, `NUXT_MAIL_*`).
- **Décision utilisateur PROD-1 (2026-10-21, decisions.md, commit a8692fd)** : le garde-fou entre dans la vague 3a, **sans aucun mode recette** qui le désactive. Le premier déploiement réel attend le domaine (OPS-4) et un SMTP.
- Le garde-fou s'applique aussi aux **scripts d'exploitation** qui utilisent cette configuration hors de Nitro : `user:create-admin` construit le lien d'invitation depuis `siteUrl`, il refuse donc, avec l'indicateur, les mêmes conditions. Une seule fonction pure (`assertStrictRuntimeConfig`) est partagée par le plugin Nitro et par le script.
- Tests : refus au démarrage pour chaque condition, démarrage réussi quand tout est valide, aucun effet sur les tests d'API. Section Coolify du README : `NUXT_STRICT_RUNTIME_CONFIG` (posé par l'image), `NUXT_PUBLIC_SITE_URL`, `NUXT_MAIL_TRANSPORT`, `NUXT_MAIL_HOST`, `NUXT_MAIL_PORT`, `NUXT_MAIL_SECURE`, `NUXT_MAIL_USER`, `NUXT_MAIL_PASSWORD` et `NUXT_MAIL_FROM` obligatoires.
- À faire par dev-b09 en commit supplémentaire, en priorité dès qu'un poste de dev actif se libère (PAR-1).

## Validation

- Email au format RFC raisonnable, 254 caractères au plus.
- Téléphone : on réutilise `PHONE_PATTERN` (src/consts/auth.const.ts, B-08), le même format que `PATCH /moi`, sans second format (revue du 2026-10-21).
- `displayName` d'un nouveau compétiteur : « Prénom Nom », la forme des 145 noms de l'archive ; le pseudo reste un champ séparé.
- Champs texte bornés en longueur.
- `avatar` : tranché par AV-1 (2026-10-20). Il n'est **pas** un champ de création ; il se téléverse après coup par `PUT /api/v1/competiteurs/{id}/avatar` (admin) ou `PUT /api/v1/moi/avatar` (participant), voir B-16.

## Critères d'acceptation

- [ ] Tests d'API :
  - la création envoie un email (adaptateur de test qui capture) ;
  - le jeton en clair n'est jamais stocké ;
  - le jeton est consommé une seule fois : un second `POST` renvoie 410 ;
  - un jeton expiré (au-delà de 7 jours, A14) renvoie 410 ;
  - après un renvoi, l'ancien lien renvoie 410 et le nouveau fonctionne.
- [ ] Tests d'API : un email déjà pris renvoie 409, sans création partielle (rollback vérifié).
- [ ] Tests d'API : avec un adaptateur en échec, le compte est créé, `invitationSent: false`, et le renvoi fonctionne.
- [ ] Le lien d'invitation est construit depuis `runtimeConfig.public.siteUrl`, jamais depuis l'en-tête `Host`.
- [ ] `/security-review` est passé : le jeton est la seule surface non authentifiée qui donne un compte (ST, « Sécurité »).

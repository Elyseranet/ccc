# B-12 — Scores : enregistrer, valider (idempotent), corriger

- **Statut** : À faire, une fois B-08 livré. A15 tranché le 2026-10-20.
- **Vague** : 3. Il tourne en parallèle de B-10 et B-11, sur des fixtures de matchs.
- **Worktree** : `../CCC-B-12`, branche `feature/B-12-scores`
- **Dépendances** : B-08, B-02 et B-03 (`validateScore`, `computePoolStanding`).

## Endpoints

Toutes ces routes sont réservées à l'**administrateur**.

| Méthode et chemin | Règles |
|---|---|
| `PUT /api/v1/matchs/{id}/score` | « Enregistrer » : écrit `recorded_score` sur chaque côté, et le match passe à `RECORDED`. Il est idempotent par nature. Aucun effet public |
| `POST /api/v1/matchs/{id}/validation` | « Valider » : RG22 (cible 5 ou 10) et tour ouvert ; copie `recorded_score` dans `validated_score` ; recalcule le classement de poule ou verse le vainqueur au vivier du tour suivant. La réponse contient **l'état recalculé** (match, classement de poule ou tour), comme l'exige la Spec API |
| `POST /api/v1/matchs/{id}/correction` | A15 : `{ scores }` + `If-Match`. Réécrit `recorded_score` et `validated_score`, recalcule classement et qualification dans une transaction, **journalise** l'ancien et le nouveau score (`match.corrected`, avec `userId`). 409 `NEXT_ROUND_ENGAGED` si un tour suivant est engagé (ARCHITECTURE, décision du 2026-10-10). Ajout à la Spec API |

| `GET /api/v1/admin/editions/{id}/matchs?statut=&tour=&poule=` | **Ajout à la Spec API** (C6) : vue admin, qui renvoie `IAdminMatch` avec le score **saisi**. `statut` est une liste de `MATCH_STATUS` ; le front compose ses filtres (« À traiter », « Saisis », « Sans score », « Validés ») en listes de statuts, et le serveur n'a pas de sémantique propre à ces filtres. 401 ou 403 hors administrateur |

## Idempotence et concurrence

C'est l'appel le plus rejoué : téléphone, connexion incertaine.

- **Transition d'état** :
  - valider un match `VALIDATED` dont `validated_score` est égal aux scores envoyés renvoie 200 avec l'état courant, sans aucun effet de bord ;
  - avec des scores différents, renvoie 409 `MATCH_ALREADY_VALIDATED`.
- **Le corps de la validation contient les scores attendus** (`{ scores: [{participationId, score}] }`). On valide ce que l'organisateur a vu, pas l'état du serveur au moment de l'arrivée.
- **Verrouillage optimiste** : `version` (`@VersionColumn`) et en-tête `If-Match`. Une version périmée renvoie 409 `MATCH_VERSION_CONFLICT`, ce qui couvre le cas « validé par une autre session » de `parcours.md` §6.
- La validation, le recalcul et la qualification se font dans **une transaction** (invariant 5).
- **Pas de table de clés d'idempotence** : la détection par l'état suffit (ARCHITECTURE en laisse le choix). C'est à revoir en revue si un cas non couvert apparaît.

## Refus

| Cas | Statut |
|---|---|
| Score négatif, non entier, côté absent, participant étranger au match | 400 |
| Aucun ou deux vainqueurs, vainqueur ≠ cible (RG22) | 422 `SCORE_INCONSISTENT` |
| Match d'un tour non ouvert, ou édition `CLOSED` | 409 |
| `PUT` sur un match `VALIDATED` | 409 (passer par la correction) |

## Observabilité

- Un événement `match.validated` porte `matchId`, `editionId`, `userId`, `durationMs` et `replayed: boolean`.
- Le compteur des rejeux est visible dans les logs : il permet de mesurer la qualité réseau d'une soirée.

## Critères d'acceptation

- [ ] Tests d'API :
  - le même `POST validation` envoyé trois fois donne un seul effet (classement identique), avec trois réponses 200 identiques ;
  - un `If-Match` périmé renvoie 409 ;
  - un score 5-5 renvoie 422 ;
  - 10-9 en finale est valide.
- [ ] Tests d'API : avant validation, l'endpoint public de B-06 ne montre pas le score ; après validation, il le montre.
- [ ] Tests d'API : la réponse de validation contient le classement de poule recalculé.
- [ ] Tests d'API (correction, A15) : acceptée avant que le tour suivant soit engagé, avec classement recalculé et événement `match.corrected` journalisé ; refusée en 409 après ; `If-Match` périmé → 409 ; score incohérent → 422.
- [ ] « Tour suivant engagé » est défini ainsi (R-3, validé par l'utilisateur le 2026-10-20) : pour un match de poule, la qualification est arrêtée ; pour un match de phase finale, un tirage (même `DRAFT`) existe pour le tour suivant.
- [ ] Participant renvoie 403, anonyme renvoie 401, y compris sur la vue admin des matchs.
- [ ] Test dédié : `recordedScore` et `comment` (A13) n'apparaissent dans **aucune** route hors `/api/v1/admin/`.
- [ ] Tests d'API : `statut` accepte une liste de statuts (`?statut=RECORDED&statut=SCHEDULED`) ; un statut hors `MATCH_STATUS` renvoie 400. La correspondance des filtres de F-08, établie par le front d'après `admin-scores.html`, est la suivante : À traiter = RECORDED + SCHEDULED, Saisis = RECORDED, Sans score = SCHEDULED, Validés = VALIDATED. `RESULT_UNKNOWN` (archive) n'apparaît dans aucun filtre.

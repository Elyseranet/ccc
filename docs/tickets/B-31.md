# B-31 — Inviter, gérer et retirer un administrateur depuis l'interface

- **Statut** : Ouvert : prêt à implémenter (2026-11-18). Décisions utilisateur Q1 à Q5, Q9, Q10 du 2026-11-18 (via le chef de projet).
- **Demande utilisateur (2026-11-18)** : avant la remise au client, pouvoir inviter un administrateur depuis l'interface (liste des admins, invitation par email, renvoi / correction tant que non activé, retrait d'un accès). Écran `/admin/administrateurs`, accessible depuis « Plus » et le tiroir, groupe Référentiel (front, ticket F du frontend-lead).
- **Constat (code vérifié le 2026-11-18)** : un administrateur ne se crée qu'en CLI (`npm run user:create-admin`, `src/utils/create-admin-cli.util.ts` → `createAdminWithInvitation`, `src/utils/create-admin.util.ts`) : compte `ADMIN` / `INVITED` sans fiche, lien affiché une fois, aucun mail. Aucune route ne liste, n'invite ni ne retire un administrateur. `USER_STATUS` n'a que `INVITED` / `ACTIVE`. `resolveSession` relit rôle et statut à chaque requête. Le mail d'invitation (F-66, `src/consts/invitation-email-template.const.ts` l. 68 et 153) dit « vous a inscrit comme participant ».
- **Contrat** : `docs/api/administrateurs.md`, section B-31 — `GET` / `POST /api/v1/admin/administrateurs`, `POST /admin/administrateurs/{id}/invitation`, `PATCH` / `DELETE /admin/administrateurs/{id}` ; nouveaux codes `ALREADY_ADMIN`, `LAST_ADMIN`, `CANNOT_REVOKE_SELF` ; entrées `API_ROUTES` avec `pendingTicket: 'B-31'`, retiré dans le commit qui livre chaque route.
- **Décisions utilisateur (2026-11-18)** :
  - **Q1** : un administrateur ACTIF retiré redevient `PARTICIPANT`, toutes ses sessions sont révoquées ; fiche, mot de passe et auteur de ses validations conservés. Pas de statut désactivé, pas de migration.
  - **Q2** : une invitation d'administrateur jamais activée, sans fiche, retirée → compte supprimé (invitations en cascade, lien 404).
  - **Q3** : pas d'auto-retrait → 409 `CANNOT_REVOKE_SELF`.
  - **Q4** : inviter l'email d'un compte joueur existant → promotion du même compte (`role` → ADMIN, fiche conservée) ; INVITED : nouvelle invitation, variante admin ; ACTIVE : voir Q5.
  - **Q5** : un joueur ACTIF promu reçoit un mail d'information **sans lien de connexion**.
  - **Q9** : logs structurés seulement (`LOG_EVENT`, sans email ni jeton ni lien), A17 inchangé, pas de table d'audit.
  - **Q10** : texte du mail d'invitation administrateur validé **mot pour mot** : sujet « Votre accès administrateur à la Cotentin Caps Cup » ; phrase « L'organisateur de la Cotentin Caps Cup vous a donné un accès administrateur : un compte vient de vous être créé sur le site du CCC. » (remplace, dans la variante admin seulement, la phrase « vous a inscrit comme participant » ; le reste du gabarit F-66 est inchangé, version HTML et texte).
- **Point ouvert, à valider avant merge** : le **texte du mail d'information de promotion (Q5)** n'a pas été rédigé ni validé ; seule sa nature est décidée (information, sans lien). Le dev le rédige sur le gabarit F-66 et le chef de projet le fait valider par l'utilisateur.
- **Réutiliser (pas de doublon)** :
  - émission / invalidation des liens : `issueInvitation` (`src/utils/invitation-store.util.ts`, déjà partagé avec la CLI) ;
  - envoi après commit, échec non bloquant et journalisé : `sendInvitationEmail` (`src/services/invitation.service.ts`), étendu d'une variante ;
  - corps du mail : `buildInvitationEmail` (`src/utils/invitation-email.util.ts`) — variante administrateur et mail de promotion dans le même gabarit F-66, pas un second gabarit ;
  - correction d'email d'un INVITED : extraire de `setCompetitorAccountEmail` (`src/services/competitor.service.ts`) la partie « remplacer l'email + réémettre », la partager avec `PATCH /admin/administrateurs/{id}` ;
  - collision d'email concurrente : `isEmailCollision` ; normalisation : `normalizeEmail` ; schéma email : `adminEmailSchema` (`src/server/schemas/auth.schema.ts`) ;
  - révocation : ajouter dans `src/utils/session-store.util.ts` une fonction « toutes les sessions d'un compte », sur le modèle de `revokeOtherSessions` ;
  - garde de rôle : `requireRole` ; erreurs : `src/utils/api-error.util.ts` ; logs : `logger` + `LOG_EVENT`.
  - La CLI `user:create-admin` reste (premier administrateur, secours), sans changement.
- **Sécurité** : `docs/api/administrateurs.md`, section Sécurité (tout admin actif gère les admins ; dernier admin actif protégé sous verrou `FOR UPDATE` des comptes ADMIN ; rétrogradation immédiate + sessions révoquées ; pas de surface publique ajoutée ; pas de limite de débit, comme A14 et B-29).
- **Critères** :
  - tests API : liste (401 anonyme, 403 participant, aucun hash sérialisé, admin INVITED présent avec son échéance) ; invitation d'un email inconnu → compte ADMIN INVITED + mail variante admin dans le fichier de capture (sujet et phrase Q10 exacts, aucun « participant ») ; email déjà admin 409 `ALREADY_ADMIN` ; promotion d'un PARTICIPANT INVITED (même compte, fiche conservée, ancien lien 410, mail variante admin) ; promotion d'un PARTICIPANT ACTIVE (rôle ADMIN, sessions conservées, mail d'information sans lien) ; renvoi (ancien lien 410) ; correction (ancien lien 410, le nouvel email reçoit le mail) ; correction d'un actif 409 `ACCOUNT_ACTIVE` ; retrait d'un actif → rôle PARTICIPANT, sessions révoquées, la requête suivante de sa session répond 401 ; retrait d'un INVITED sans fiche → compte supprimé, lien 404 ; retrait du dernier admin actif 409 `LAST_ADMIN` ; deux retraits croisés concurrents laissent au moins un admin actif ; auto-retrait 409 `CANNOT_REVOKE_SELF` ;
  - test unitaire du gabarit : variante admin (texte Q10), mail de promotion sans lien, variante joueur inchangée ;
  - typecheck, `test:run`, `test:release`, `test:bundle`, test:api concernés verts ; Spec API à jour ; aucune migration.
- **Front** : écran « Administrateurs » (`/admin/administrateurs`, « Plus » + tiroir groupe Référentiel), ticket F à ouvrir par le frontend-lead.

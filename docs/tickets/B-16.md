## Contrat d'API

| Méthode et chemin | Accès | Corps / réponse | Refus |
|---|---|---|---|
| `PUT /api/v1/moi/avatar` | authentifié, sur **son** compétiteur | `multipart/form-data`, un seul champ `file` → `200 { avatarUrl }` | voir le tableau des erreurs |
| `DELETE /api/v1/moi/avatar` | authentifié | → `204` ; l'avatar redevient `null` (initiales côté front) | 404 si aucun avatar |
| `PUT /api/v1/competiteurs/{id}/avatar` | administrateur | même contrat | 403 hors admin, 404 si le compétiteur est inconnu |
| `DELETE /api/v1/competiteurs/{id}/avatar` | administrateur | → `204` | idem |
| `GET /api/v1/competiteurs/{id}/avatar` | **public** (P5.4 : les fiches publiques affichent l'avatar) | les octets de l'image | 404 si aucun avatar |

**Création d'un participant avec photo (F-09).** Elle se fait en deux appels :
1. `POST /api/v1/editions/{id}/participants` avec `newCompetitor`, qui renvoie le `competitorId` ;
2. `PUT /api/v1/competiteurs/{competitorId}/avatar`.

Ce découpage garde la création du compte en JSON, dans sa transaction (B-09/B-10), et évite un corps multipart mêlé à des données de compte. Si l'étape 2 échoue, le compétiteur existe déjà sans photo : le front propose de réessayer.

**`avatarUrl` dans les DTO.**
- `ICompetitorPublic.avatarUrl` vaut `/api/v1/competiteurs/{id}/avatar?v={empreinte}`, ou `null` sans avatar. L'empreinte correspond aux 16 premiers caractères du SHA-256 du contenu stocké, ce qui fait changer l'URL à chaque nouvel avatar.
- Le champ `avatarUrl` (URL https saisie) est **retiré** de la liste blanche de `PATCH /moi` et de `newCompetitor` : l'avatar ne se pose plus que par téléversement. C'est un amendement de B-08 et de B-09.

## Traitement du fichier

1. **Taille** : lecture **en flux**, avec un arrêt et 413 dès que 2 Mo (`AVATAR_MAX_BYTES = 2 * 1024 * 1024`) sont dépassés. Le corps n'est jamais chargé entièrement avant le contrôle. Les en-têtes `Content-Length` annonçant plus de 2 Mo sont refusés immédiatement.
2. **Type par signature** (les octets magiques, jamais l'extension ni le `Content-Type` déclaré) :
   - JPEG : `FF D8 FF` ;
   - PNG : `89 50 4E 47 0D 0A 1A 0A` ;
   - WebP : `RIFF....WEBP`.

   Toute autre signature renvoie 415.
3. **Ré-encodage avec suppression des métadonnées** par la bibliothèque `sharp` :
   1. application de l'orientation EXIF (`.rotate()`), sans quoi une photo de téléphone s'afficherait couchée une fois l'EXIF retiré ;
   2. redimensionnement à 512 px de côté au plus (`AVATAR_MAX_DIMENSION_PX`), sans agrandissement ;
   3. ré-encodage dans le même format, sans `withMetadata()`, ce qui supprime EXIF (dont le GPS), XMP et IPTC.

   Le décodage d'un fichier corrompu renvoie 422.
4. **Stockage** : remplacement de l'avatar précédent dans une seule transaction.

### Bibliothèque retenue : `sharp`, version épinglée

- Dépendance : `"sharp": "0.35.5"`, en **version exacte**, sans `^` : le binaire natif libvips suit la version.
- Licences : `sharp` est sous **Apache-2.0** ; `@img/sharp-libvips-*` 1.3.4 sous **LGPL-3.0-or-later**, utilisée sans modification. Validé par l'utilisateur (AV-2, 2026-10-20, `decisions.md`). Les deux licences sont à reprendre dans les mentions de licences du projet.

### Pourquoi `sharp` plutôt qu'un nettoyage maison

| Critère | `sharp` 0.35.5 | Nettoyage maison (retrait des segments APPn JPEG, des chunks PNG `eXIf`/`tEXt`, des chunks WebP `EXIF`/`XMP`) |
|---|---|---|
| Orientation | appliquée avant retrait | **perdue** : photos couchées |
| Fichiers piégés (polyglottes, segments malformés) | neutralisés par le décodage et le ré-encodage | recopiés tels quels si le parseur les tolère |
| Taille stockée | réduite par le redimensionnement | inchangée, jusqu'à 2 Mo |
| Coût | une dépendance native (libvips) | environ 150 lignes de parseurs binaires à maintenir et à tester |

## Service de l'image

`GET /api/v1/competiteurs/{id}/avatar` :
- `Content-Type` = le type **détecté et stocké** (`image/jpeg`, `image/png` ou `image/webp`) ;
- `X-Content-Type-Options: nosniff` ;
- `Content-Disposition: inline` ;
- `Content-Security-Policy: default-src 'none'` ;
- `ETag` = empreinte SHA-256 ;
- `Cache-Control: public, max-age=31536000, immutable` quand la requête porte le bon `?v=` ; sinon `Cache-Control: no-cache` et revalidation par ETag (304).

## Critères d'acceptation

- [ ] **GPS absent après upload** : une fixture JPEG portant des balises EXIF GPS est téléversée ; les octets servis par `GET …/avatar` ne contiennent plus aucun bloc EXIF ni GPS (vérification par lecture des segments, ou par `sharp().metadata()` qui ne renvoie plus `exif`).
- [ ] **Orientation** : une fixture avec `Orientation = 6` est servie redressée (largeur et hauteur permutées), sans balise d'orientation.
- [ ] **Trop gros refusé** : un fichier de 2 Mo + 1 octet renvoie 413, et le flux est interrompu sans tout lire (test sur un flux plus long qui s'arrête au seuil). Un `Content-Length` supérieur à 2 Mo renvoie 413 immédiatement.
- [ ] **Faux type refusé** : un fichier texte renommé `.jpg` et envoyé en `Content-Type: image/jpeg` renvoie 415. Un GIF renvoie 415. Un JPEG tronqué renvoie 422.
- [ ] Les trois formats acceptés passent ; l'image servie a le `Content-Type` détecté, ainsi que `nosniff` et la CSP.
- [ ] Cache : 200 puis 304 avec l'ETag ; `?v=` correct → `immutable` ; un nouvel upload change `avatarUrl`.
- [ ] Droits :
  - un participant ne peut téléverser que pour lui (`/moi/avatar`) ;
  - `PUT /competiteurs/{id}/avatar` renvoie 403 pour un participant et 401 pour un anonyme ;
  - `GET` est public.
- [ ] `PATCH /moi` et `newCompetitor` refusent désormais `avatarUrl` (400, hors liste blanche). Ce critère **ferme L7 de T-SEC-04** (pistage des visiteurs par une URL d'avatar externe) dans le même tour que le merge de B-16.
- [ ] Aucun DTO public n'expose `content`, `sha256` ni `byte_size`.
- [ ] Migration up/down/up sur base neuve ; `npm ls axios` vide ; `npm audit` sans écart par rapport à AUDIT-1 ; `npm run build` puis démarrage de l'image Docker Linux avec `sharp` chargé (test de fumée sur une route d'upload).
- [ ] La doc d'API (`docs/api/avatar.md`) et le README sont à jour.

# B-32 — Relier un compte administrateur à sa fiche joueur (un seul compte par personne)

- **Statut** : Ouvert : implémenté sur `feature/B-32-link-admin-card` @ `499acb03` (non mergé, attend B-31). Branche : typecheck vert, `test:run` 1561 / 0, API admin-link + invitations 30/30, revue de sécurité manuelle sans vulnérabilité à haute confiance. Règle ajoutée (conséquence de Q8 et de la maquette F-69) : une fiche reliée à un compte ADMIN (INVITED ou ACTIVE) est verrouillée, tout PUT répond 409 `ACCOUNT_ALREADY_LINKED`. (2026-11-18) Décisions utilisateur Q6 à Q8 du 2026-11-18 (via le chef de projet), et Q4 de B-31.
- **Demande utilisateur (2026-11-18)** : un administrateur qui joue garde UN seul compte, rattaché à sa fiche joueur (pour ses stats).
- **Constat (code vérifié le 2026-11-18)** : un compte a au plus une fiche (`users.competitor_id`, `uq_users_competitor_id`). `PUT /competiteurs/{id}/compte` (B-29, `setCompetitorAccountEmail`) répond 409 `EMAIL_ALREADY_USED` dès que l'email appartient à un compte, donc à l'admin. Un admin CLI n'a pas de fiche. Les stats sont calculées par fiche, pas par compte : relier le compte suffit.
- **Deux chemins vers « un seul compte »** :
  1. le joueur a déjà un compte → il est **promu** admin (B-31, Q4) ; rien à relier ;
  2. l'admin a déjà un compte (CLI ou invitation admin) → on **relie** son compte à la fiche existante : objet de ce ticket.
- **Décisions utilisateur (2026-11-18)** :
  - **Q6** : n'importe quel administrateur relie, **depuis la fiche joueur**, via `PUT /competiteurs/{id}/compte` étendu. **Pas** de variante « Ma fiche joueur » côté `/profil` (pas de `PUT /moi/fiche`). Côté écran : l'admin est choisi dans la liste `GET /admin/administrateurs` (B-31) ; un admin encore INVITED est sélectionnable, avec la mention « invité ».
  - **Q7** : la fiche a un compte joueur INVITED (jamais activé) → ce compte est supprimé (invitations en cascade, ses liens 404) et l'admin prend la fiche. Fiche à compte ACTIVE → refus 409 `ACCOUNT_ACTIVE` (pas de fusion).
  - **Q8** : **pas de déliaison** : aucune route `DELETE /competiteurs/{id}/compte` ; une erreur de lien se corrige en base par l'exploitant.
- **Contrat** : `docs/api/administrateurs.md`, section B-32 — extension de `PUT /competiteurs/{id}/compte` (email d'un compte ADMIN sans fiche, INVITED ou ACTIVE → lien) ; `IAccountEmailSet` gagne `linked`, `accountStatus` s'élargit à `USER_STATUS`, `invitationExpiresAt` devient nullable ; nouveau code `ACCOUNT_ALREADY_LINKED`. Aucune nouvelle entrée `API_ROUTES` (`COMPETITOR_ACCOUNT_EMAIL_SET` existe).
- **Réutiliser** : `setCompetitorAccountEmail` (verrou de la fiche déjà en place, contrôle d'email, traduction de collision) — y ajouter la branche « lien », pas une seconde fonction ; `isEmailCollision` à étendre à la contrainte `uq_users_competitor_id` (→ 409 `ACCOUNT_ALREADY_LINKED`) ; `logger` + `LOG_EVENT` (`admin_competitor_linked`, avec `replacedInvitedUserId` si Q7 a supprimé un compte ; jamais d'email).
- **Critères** :
  - tests API : admin ACTIVE sans fiche relié à une fiche sans compte (200 `linked: true`, `GET /moi` de l'admin porte la fiche (`competitor` non nul), aucun mail envoyé) ; admin INVITED relié (200, `accountStatus: INVITED`, son invitation reste valable) ; fiche avec compte INVITED → compte supprimé, son ancien lien 404, admin relié ; fiche avec compte ACTIVE 409 `ACCOUNT_ACTIVE` ; admin déjà relié ailleurs 409 `ACCOUNT_ALREADY_LINKED` ; email d'un PARTICIPANT toujours 409 `EMAIL_ALREADY_USED` ; deux PUT concurrents du même admin vers deux fiches → une seule réussit ; 403 participant ;
  - non-régression B-29 : les tests invitations existants restent verts (contrat élargi, `linked: false` sur les cas B-29) ;
  - typecheck, `test:run`, `test:release`, `test:bundle`, test:api concernés verts ; Spec API à jour ; aucune migration.
- **Front** : F-62 doit lire `linked` et le nouveau `accountStatus`, et proposer le sélecteur d'administrateur (mention « invité ») ; ticket F à ouvrir par le frontend-lead.

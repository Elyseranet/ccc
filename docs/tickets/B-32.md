# B-32 — Relier un compte administrateur à sa fiche joueur (un seul compte par personne)

- **Statut** : À faire (2026-11-18) — **bloqué par les arbitrages Q6 à Q8** (et Q4 de B-31). Ne pas implémenter avant la décision utilisateur.
- **Demande utilisateur (2026-11-18)** : un administrateur qui joue garde UN seul compte, rattaché à sa fiche joueur (pour ses stats).
- **Constat (code vérifié le 2026-11-18)** : un compte a au plus une fiche (`users.competitor_id`, `uq_users_competitor_id`). `PUT /competiteurs/{id}/compte` (B-29, `setCompetitorAccountEmail`) répond 409 `EMAIL_ALREADY_USED` dès que l'email appartient à un compte, donc à l'admin. Un admin CLI n'a pas de fiche (`competitor_id` nul). Les stats sont calculées par fiche, pas par compte : relier le compte suffit.
- **Deux chemins vers « un seul compte »** :
  1. le joueur a déjà un compte → il est **promu** admin (B-31, Q4) ; rien à relier ;
  2. l'admin a déjà un compte (CLI ou invitation admin) → on **relie** son compte à la fiche existante : objet de ce ticket.
- **Contrat proposé** : `docs/api/administrateurs.md`, section B-32 — extension de `PUT /competiteurs/{id}/compte` (cas « email d'un compte ADMIN sans fiche » → lien), `IAccountEmailSet` gagne `linked` et un `invitationExpiresAt` nullable ; nouveau code `ACCOUNT_ALREADY_LINKED` ; `DELETE /competiteurs/{id}/compte` selon Q8 (`pendingTicket: 'B-32'`).
- **Réutiliser** : `setCompetitorAccountEmail` (verrou de la fiche déjà en place, contrôle d'email, traduction de collision) — y ajouter la branche « lien », pas une seconde fonction ; `isEmailCollision` à étendre à la contrainte `uq_users_competitor_id` ; `logger` + `LOG_EVENT`.
- **Critères** :
  - tests API : admin sans fiche relié à une fiche sans compte (200 `linked: true`, `GET /moi` porte la fiche (`competitor` non nul), stats de la fiche visibles) ; fiche avec compte INVITED selon Q7 ; fiche avec compte ACTIVE 409 `ACCOUNT_ACTIVE` ; admin déjà relié ailleurs 409 `ACCOUNT_ALREADY_LINKED` ; email d'un PARTICIPANT toujours 409 `EMAIL_ALREADY_USED` ; deux PUT concurrents vers deux fiches → une seule réussit ; 403 participant ; délier selon Q8 ;
  - non-régression B-29 : les 18 tests invitations restent verts ;
  - typecheck, `test:run`, `test:release`, `test:bundle`, test:api concernés verts ; Spec API à jour ; aucune migration.
- **Front** : F-62 doit lire `linked` et le nouveau `accountStatus` (ticket F à ouvrir par le frontend-lead).

## Arbitrages à poser à l'utilisateur

**Q6 — Qui relie une fiche à un compte administrateur, et depuis où ?**
- (a) **Recommandé** : n'importe quel admin, depuis la fiche joueur, en saisissant l'email de l'admin dans le champ « email » existant (F-62). Aucune nouvelle route d'écriture, presque aucun travail front.
- (b) L'admin lui-même, depuis son compte (`PUT /moi/fiche` avec la fiche choisie) : nouvelle route et nouvel écran ; il ne peut relier que son propre compte.
- (c) Les deux : double coût.

**Q7 — La fiche a déjà un compte joueur INVITED (jamais activé, autre email)**
- (a) **Recommandé** : le compte INVITED du joueur est supprimé (son lien répond 404) et le compte admin prend la fiche. Ce compte n'a jamais servi, rien n'est perdu.
- (b) Refus 409 : l'admin doit d'abord corriger l'email de l'invitation… impossible sans supprimer ce compte, donc impasse.
- Dans tous les cas, une fiche avec un compte **ACTIF** est refusée (409 `ACCOUNT_ACTIVE`) : fusionner deux comptes actifs (mots de passe, sessions, appareils) est hors périmètre.

**Q8 — Pouvoir délier un compte admin de sa fiche (erreur de saisie)**
- (a) **Recommandé** : oui, `DELETE /competiteurs/{id}/compte`, réservé aux comptes admin. Sans elle, une erreur de lien ne se corrige qu'en base.
- (b) Non : correction en base par l'exploitant.

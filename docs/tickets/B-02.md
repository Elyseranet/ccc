## Modèle d'entités

Tables au pluriel, colonnes en `snake_case` via `SnakeNamingStrategy`, et clés `uuid` (`gen_random_uuid()`, PostgreSQL 16). Les compteurs sont des `integer`. Les points sont en `numeric(7,2)`, ce qui est exact parce que `base × N / 50 = base × N × 0,02` tombe toujours sur deux décimales (RG2).

Les identités (`users`, `sessions`, `invitations`) **ne font pas partie de ce ticket** : elles sont portées par B-08 (session en base, A2 tranché) et B-09. `validated_by_user_id` et `created_by_user_id` restent des `uuid` nullables, sans FK ; B-08 ajoute les FK.

### Pourquoi deux colonnes de score

Le score saisi (`recorded_score`) et le score validé (`validated_score`) sont distincts (invariant 4). Le public ne lit **que** `validated_score` : un score non validé n'est jamais public (décision E-f). Une correction (ARCHITECTURE, décision du 2026-10-10) réécrit `validated_score` de façon atomique, sans faire disparaître le score public entre deux appels.

### Ce qui n'est pas une table

Classements ACP et All Time, évolution (RG8), face-à-face (RG36, RG37), statistiques V/D (RG7) et classement de poule (RG19) sont calculés à la lecture par les fonctions de B-03. Volume réel : 145 compétiteurs, 16 éditions. Aucune matérialisation sans mesure préalable (ST, « Ce qui n'est pas une table »).

## DTO — `../../src/shared/interfaces/api/`

Un fichier par ressource. Ce sont des DTO de **sortie** : les routes ne renvoient jamais d'entité TypeORM.

- `competitor.interface.ts` : `ICompetitorPublic { id, displayName, firstName, lastName, nickname, avatarUrl }`. **Aucun** `email` ni `phone`. `ICompetitorListItem` l'étend avec les statistiques de liste (C4) : `editionsPlayed`, `matchesPlayed`, `wins`, `titles`, `firstEditionCode`. `ICompetitorDetail` l'étend avec `participations: ICompetitorParticipation[]` et `stats: ICompetitorStats { played, wins, losses, pointsFor, pointsAgainst, titles }`.
- `edition.interface.ts` : `IEditionSummary { id, code, year, name, heldOn, location, status, origin, participantCount, matchCount, scoredMatchCount, champion: IEditionChampion | null }` (C1, C2), avec `IEditionChampion { competitor: ICompetitorPublic, titlesToDate }` et `IEditionDetail`, qui ajoute participants, poules, tours, matchs, tirages et bracket.
- `match.interface.ts` : `IMatch { id, sequence, roundKind, poolRank, purpose, targetScore, status, sides: IMatchSide[], winnerParticipationId }`. **Pas de `comment` côté public** (A13 : commentaires visibles par l'administrateur uniquement) ; il est porté par `IAdminMatch`. `IMatchSide { participationId, competitorId, displayName, score }`. `score` vaut `validated_score` côté public et `null` si le match n'est pas validé.
- `pool.interface.ts` (`IPool`, `IPoolStandingRow`), `round.interface.ts` (`IRound`, avec `matchCount` et `validatedMatchCount`, C3), `draw.interface.ts` (`IDraw`, `IDrawAssignment`).
- `ranking.interface.ts` : `IRankingRow { rank, competitor, points, participations, average, titles }` et `IRankingEvolutionPoint`, plus `IRankingEvolutionSeries { competitor, points: IRankingEvolutionPoint[] }` (C5).
- `stats.interface.ts` : `IArchiveStats { editions, competitors, matches, scoredMatches }` (C1).
- DTO **admin**, dans des fichiers à part, jamais renvoyés par une route publique :
  - `admin-match.interface.ts` : `IAdminMatch extends IMatch`, avec `comment` (A13), `sides[].recordedScore`, `recordedAt`, `validatedAt` et `validatedBy` (C6, porté par B-12) ;
  - `admin-activity.interface.ts` : `IAdminActivityItem`, porté par B-15 (C7).
- `head-to-head.interface.ts` : `IHeadToHead`.

Les champs JSON sont en camelCase anglais et les chemins d'URL en français, comme dans la Spec API. Toute divergence avec le front se tranche dans ce ticket, avant merge.

## Plan de migrations

| # | Migration | Ticket | `down` |
|---|---|---|---|
| existante | `1760131200000-CreateLegacyWorkbookImportTables` | — | supprime les tables d'archive |
| M1 | `CreateDomainSchema` : `competitors`, `competitor_aliases`, `editions`, `pools`, `rounds`, `participations`, `matches`, `match_sides`, `draws`, `draw_assignments`, plus les extensions `pg_trgm` et `unaccent` si retenues pour la recherche | B-02 | `DROP` en ordre inverse des FK ; les extensions ne sont **pas** supprimées (elles peuvent servir ailleurs), ce qui est documenté |
| M2 | `CreateIdentitySchema` : `users`, `sessions` (A2 : session en base), `invitations`, et FK de `validated_by_user_id` et `created_by_user_id` vers `users` | B-08 | supprime les FK puis les tables |
| M3+ | ajustements révélés par B-11 à B-13 (par exemple les colonnes de qualification) | au besoin | `up` et `down` à chaque fois |

Règles :
- les migrations sont générées par `npm run db:migration:generate`, puis relues à la main ;
- jamais de `synchronize` ;
- le rollback de M1 détruit toutes les données métier, **y compris celles importées par B-04**. Elles se reconstruisent par `db:import:legacy`, puisque l'archive brute reste intacte. Ce point est écrit dans le README.

# B-18 — Ne pas publier les tours non tirés (`ROUND_STATUS.PENDING`)

- **Statut** : Ouvert (2026-10-28). Décision utilisateur QA-2, mise en œuvre (`docs/design/ux/decisions.md`).
- **Bloque** : T-QA-03, donc F-01. Sert aussi F-07, F-08 et F-11.
- **Constat**, lu dans le code :
  - `GET /editions/{id}` charge tous les matchs de l'édition, sans filtre de statut (`src/services/edition.service.ts:93-98`) ;
  - le tableau est construit par `buildBracket(rounds, matches)` (`src/utils/edition-assemble.util.ts:86-90`), sur tous les tours hors POOLS, sans filtre sur `round.status` ;
  - les côtés sont toujours publiés avec le nom du joueur (`match-public.mapper.util.ts`) ;
  - `GET /editions/{id}/matchs` sans `statut` liste aussi les matchs SCHEDULED (`edition-query.util.ts:10-24`) ;
  - `ROUND_STATUS` (`src/enums/round.enum.ts:11-16`) n'est lu par aucun service ni mapper.
- **À faire** :
  1. exclure du tableau public et de la liste publique des matchs les tours en `ROUND_STATUS.PENDING`, ainsi que leurs matchs ;
  2. vérifier l'effet sur les autres lectures publiques qui comptent ou listent des matchs (`/stats`, classements, face-à-face, parcours) et le documenter ;
  3. tests d'API : un tour PENDING et ses matchs n'apparaissent nulle part dans l'API publique ; un tour DRAWN, PLAYING ou COMPLETED apparaît comme aujourd'hui ;
  4. aucune suppression de données ; aucun changement de schéma, sauf justification.
- **Question à confirmer par le backend-lead** (sans trancher) : est-ce le bon comportement produit quand les tours des phases finales existeront avant leur tirage ? Je ne sais pas, car aucun code ne crée encore de tour hors du dump.
